# UI Rules

Этот документ фиксирует правила хранения и использования UI-ресурсов: окон, префабов, спрайтов, материалов, общих ассетов и feature-owned ассетов.

Документ живой: правила ниже будут активно обновляться по мере того, как проект выстраивает единую политику для UI-ресурсов.

---

## Цель

У UI-ресурсов должен быть понятный владелец. Перед добавлением нового окна, спрайта, материала или префаба нужно определить, это общий ресурс или ресурс конкретной фичи.

Это помогает не превращать `Assets/Game/Core` и общие UI-папки в склад всего подряд, а также упрощает переиспользование ресурсов между системами.

---

## 1. Общие ресурсы

Общие ресурсы - это ассеты, которые используются несколькими системами или не принадлежат одной конкретной фиче.

Примеры:

- спрайты жанров книг, потому что они загружаются и используются в разных системах;
- общие UI-спрайты;
- общие UI-материалы;
- общие префабы и ассеты для геймплейных окон.

Общие ресурсы должны храниться в общих UI- или shared-папках, а не внутри папки случайной фичи.

### 1.1 Общие gameplay UI ресурсы

К общим gameplay UI ресурсам могут относиться ассеты, которые обслуживают базовые окна или элементы геймплейного HUD.

Примеры:

- `Assets/Game/UI/GameplayScene/Prefabs/GameplaySceneController.prefab`
- общие настройки;
- общие элементы HUD;
- shared visual assets, которые нужны нескольким gameplay-окнам.

Это правило может уточняться и расширяться. Если ресурс сначала кажется feature-specific, но затем начинает использоваться несколькими системами, его нужно пересмотреть как общий ресурс.

---

## 2. Ресурсы конкретных фич

Если ресурс относится к одной конкретной фиче, он должен храниться рядом с этой фичей.

Пример:

- окно открытия локации относится к фиче открытия локации;
- окно магазина относится к фиче магазина;
- декорные UI-спрайты и префабы относятся к фиче декора, если они не переиспользуются вне неё.

Рекомендуемая структура:

```text
Assets/Game/Features/<Feature>/UI/
Assets/Game/Features/<Feature>/UI/Prefabs/
Assets/Game/Features/<Feature>/UI/Sprites/
Assets/Game/Features/<Feature>/UI/Materials/
```

Если ресурс начинает использоваться вне своей фичи, нужно явно решить: оставить его во фиче как зависимость или вынести в shared-область.

---

## 3. Shared кнопки

Общие кнопки и базовые UI-компоненты должны храниться в shared UI-области.

Текущий пример:

- `Assets/Game/UI/Prefabs`

Эта папка подходит для переиспользуемых кнопок и UI-компонентов, которые не принадлежат конкретному окну или фиче.

### 3.1 Shared UI классы

Общие классы для UI нужно помещать в `Assets/Game/Infrastructure/UIShared`.

Это место для переиспользуемых UI-компонентов и helpers, которые могут использовать разные окна и фичи:

- safe area компоненты;
- общие pool/list helpers;
- button animation;
- общие audio-компоненты для UI;
- общие presenter/registry/helper классы, не принадлежащие конкретной фиче.

Префабы при этом не обязаны жить рядом с shared-классами. Префабы могут находиться ближе к месту использования или владельцу:

- feature-owned prefab -> рядом с фичей;
- общий визуальный prefab -> `Assets/Game/UI/Prefabs` или другая shared UI папка;
- системный core prefab -> только если он действительно нужен UI-системе как инфраструктура.

---

## 4. Большие наборы спрайтов

С большим количеством спрайтов нужно работать отдельно и внимательно: часть спрайтов уже имеет большой размер, а крупные наборы могут быстро увеличить вес проекта, Addressables-бандлов и APK.

Перед добавлением или переносом большого набора спрайтов нужно проверить:

- кто владелец набора: shared UI или конкретная фича;
- какие спрайты реально используются;
- можно ли уменьшить размер, формат, packing/import settings или разбить набор;
- нужно ли грузить их сразу или лучше оставить lazy loading через Addressables/sprite provider.

Это правило особенно важно для общих спрайтов, потому что shared-ресурс легко начинает подтягиваться несколькими окнами и системами.

## 5. Core UI и префабы

`Assets/Game/Core/UI` - это core-функционал UI-системы: фактически переиспользуемый модуль, на который могут опираться окна и фичи.

В `Assets/Game/Core/UI` должна жить только логика самой UI-системы:

- менеджеры;
- базовые контроллеры;
- фабрики;
- sorting;
- stack;
- lock/filter logic;
- общие contracts и базовые abstractions окон.

Сюда нельзя добавлять конкретные feature-specific классы и логику конкретных окон. Например, логика окна инвентаря, магазина, открытия локации, декора и других фич должна жить в папке своей фичи, а не в `Assets/Game/Core/UI`.

Core UI не должен становиться основной папкой для всех визуальных ресурсов проекта.

В `Assets/Game/Core/UI/Prefabs` должны попадать только системные или действительно общие core-префабы, например:

- `UIManagerCanvas`;
- common окна уровня системы, если они используются глобально;
- инфраструктурные UI-префабы, без которых UI-система не работает.

### 5.1 Ревизия `Assets/Game/Core/UI/Common`

В `Assets/Game/Core/UI/Common` уже попали некоторые окна и классы, которые нужно будет отдельно проверить.

Правило для ревизии:

- если окно действительно системное и общее для всего проекта, оно может остаться в `Core/UI/Common`;
- если окно относится к конкретной фиче или gameplay-flow, его нужно перенести в соответствующую feature/UI область;
- при переносе нужно обновить namespace, asmdef references, Addressables address/group и prefab references.

Эта папка считается временно допустимой для уже существующих common-окон, но не должна становиться местом для новых feature-specific окон.

## 6. UI-тесты

Для UI сейчас не нужно писать автоматические тесты. Визуальные состояния, анимации, prefab-ссылки, клики, задержки и общее поведение окон проверяются вручную в Unity.

Если изменение затрагивает только UI-представление или UI-анимацию, достаточно описать ручную проверку в ответе или плане. Автотесты добавляются только для не-UI логики, конфигов, сервисов, доменных правил и других частей, которые можно надежно проверить без визуальной сцены.

---

## 7. Аудио-ассеты

Аудио-ассеты не относятся к UI только потому, что часть звуков играет из UI-компонентов.
Общие клипы лежат в `Assets/Game/Audio/{Music,Ui,Sfx}`, а правила импорта, каталог
`AudioCatalog` и фолбэки описаны в `docs/SERVICES/AUDIO_SYSTEM.md`.

Shared UI-компоненты для кликов и окон остаются в `Assets/Game/Infrastructure/UIShared/Audio`.
Сами клипы назначаются через `AudioCatalog` как дефолты или локально в serialized-поле компонента,
если конкретной кнопке/окну нужен особый звук.

## 8. Правило обновления

Этот документ должен обновляться каждый раз, когда появляется новое устойчивое правило по хранению или использованию UI-ресурсов.

Если при работе возникает спорный случай, нужно добавить сюда решение и пример пути, чтобы следующий похожий случай решался быстрее.
